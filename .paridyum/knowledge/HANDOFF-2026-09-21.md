## 1. ⛔ FIX FIRST — two migrations both numbered `0011`

| File | Where | Creates |
| --- | --- | --- |
| `0011_region_is_chosen_at_provisioning_and_never_moves.sql` | **PR #7**, committed | `tenants.region`, immutable |
| `0011_accounts_and_the_docket_instance_retrofit.sql` | **uncommitted**, on the `feat/0010-…` branch | `accounts` + `account_id` on docket's five |

`migrate.py` keys `paridyum._migrations` on `seq`. **Whichever applies first takes `0011`, and the
other is refused as drift or silently skipped.** Neither has been applied, so this is free to fix
now and expensive after the first `migrate.py apply`.

**There is a second overlap underneath it.** The uncommitted `0011` does the same work as
`0013_an_instance_is_an_account.sql` on **PR #9** — both create `accounts` and add `account_id` to
`docket_persons`, `docket_identities`, `docket_register`, `docket_events`, `docket_signatures`,
both citing ADR-0104. Two implementations of one decision.

### Recommended resolution

Keep PR #7's `0011` (it is committed, open for review, and ⏱ lossy), and renumber the newer work:

```
0010  correlation id + audit stream + grants      PR #6   (no conflict)
0011  region on tenants, immutable                PR #7   (no conflict)
0012  accounts + docket retrofit                  ← the uncommitted file, renumbered from 0011
0013  releases + release_events                   ← PR #9's 0012, renumbered, accounts block REMOVED
```

**PR #9's `0012` currently creates `accounts` itself** — that block must come out, because the
renumbered file will own it. `releases.account_id` then references a table created one migration
earlier, which is the order it already needs.

**Then delete PR #9's `0013`**, which the renumbered file supersedes.

*Either ordering works; what cannot survive is two files claiming `0011`.*

## 4. The findings that matter most

**T-G.7 is not "not done" — it is specifically wrong.** Backups run nightly (last 18h ago) to
`garage-s3.storage.svc.cluster.local`, and `garage-0` runs on **`staging-worker-2` — a node of the
cluster being backed up**. Losing the cluster loses the database *and* its backups. The off-host
credential template exists with `REPLACE` values and its real counterpart never did. The other
session is now acting on this.

**`web-dashboard` was never blocked on an OIDC client.** It had no auth code at all, it is not
declared in `applications.yaml`, and the chart's *"the pod will not start"* was false — `src/`
contained no `process.env` reads, so it would have started and served an **unauthenticated control
plane**. The BFF now exists; declaring the client is a config step, gated on **T-A20**.

**Six mechanisms read as installed while never having fired.** `console-docket`'s CI had *never
run* (missing `packages: read` → `startup_failure`, which `statusCheckRollup` reports as `none` —
indistinguishable from "no CI configured"). The `Review-budget-exception` mechanism had never
worked (missing `pull-requests: read`, and a `|| :` fallback that made a refused API call look
identical to an absent exception). Plus three absent `.claude/settings.json`, and signing silently
off. **Every one was found by trying to use the thing, never by reading it.**

**A blocked pipeline hides every failure behind it.** `console-docket`'s image failure was
diagnosed wrong twice — each time a correct reading of the outermost error.
