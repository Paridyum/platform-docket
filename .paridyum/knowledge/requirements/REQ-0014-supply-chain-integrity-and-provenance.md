# REQ-0014 — A released artifact states what is in it, who built it, and can be verified

## Status

**DEFERRED** as of 2026-08-08. Nothing is released. `tool-forge` does not exist, no service
is deployed, no crate is published, and `release.release_plz_configured` is declared against
a repository class that has no members. There is no artifact to describe, sign, or verify.

This is recorded now rather than discovered later for one reason: **provenance cannot be
retrofitted.** An SBOM generated a year after the fact describes what is in the tree today,
not what shipped; a signature added later proves who signed the file, not who built it. The
first release is the only cheap moment, and by then the context that makes these decisions
obvious will be gone.

## Requirement

**Every artifact that leaves the build system shall carry a machine-readable statement of
its components and its build provenance, and that statement shall be verifiable by a
consumer who does not trust the builder.**

## Numbered items

1. **An SBOM per artifact, generated by the build, in CycloneDX or SPDX.** Generated — never
   hand-maintained. A hand-maintained component list is the same failure as a hand-maintained
   count, which this repository has now been caught by four times, except that here it is
   security-relevant: the question an SBOM answers is "are we affected by this CVE", and the
   answer is worthless if the list is stale. Attach it to the release, do not merely archive
   it in CI logs that expire.

2. **Build provenance attestation — SLSA Build L2 as the initial target, L3 as the direction.**
   L2 wants a hosted build service producing signed provenance; GitHub Actions with
   `actions/attest-build-provenance` reaches it without new infrastructure. L3 additionally
   wants the build to be non-forgeable and isolated, which is a real cost and should not be
   claimed until it is true. State the level reached; do not claim a level as an aspiration.

2b. **For anything published to npm, this is already decided by the registry.** npm
   **permanently revoked all classic tokens on 2026-02-03**; the supported path is OIDC
   **trusted publishing**, which mints short-lived credentials from the CI workflow and
   **generates provenance attestations automatically** — no `--provenance` flag, no
   long-lived token in a secret store. Trusted-publisher configurations created after
   2026-05-20 must name at least one allowed workflow.

   This *narrows* the requirement rather than adding to it: for the `library` and `sdk`
   classes there is nothing to design, only something to switch on, and the alternative was
   withdrawn by the registry rather than rejected by us. It also removes a REQ-0001 dependency
   that would otherwise have existed — a publish token is a runtime secret needing custody,
   and under trusted publishing there is no token to hold.

3. **Signing, with a stated key custody model.** Keyless via Sigstore/Fulcio ties the
   signature to the workflow identity and avoids a long-lived key nobody can rotate, which
   is the right default for a small team. If a long-lived key is used instead, name who holds
   it and how it is rotated — an unrotatable signing key is worse than no signing, because it
   converts one compromise into permanent trust.

4. **Verification on the consuming side, or none of the above is a control.** A signature
   nobody checks is a file. Deployment must verify the attestation and refuse an unattested
   image. This is the item most likely to be skipped, because skipping it is invisible until
   it matters.

5. **Reproducibility where it is cheap, and honesty where it is not.** Pinned toolchains
   (`cargo.toolchain_file_pinned`) and lockfiles already remove most build nondeterminism. Do
   not claim reproducible builds without a check that rebuilds and compares.

6. **Dependency provenance, not only dependency versions.** `ci.actions_pinned_to_sha` and
   `cargo.no_diesel_dependency` govern what may be depended on; this governs knowing what
   actually got pulled in transitively at build time, which is the layer where the
   PackageGate-class compromises land.

## Why now, and what it costs to defer

The cost of deferral is bounded and known: nothing exists to attest, so nothing is
unprotected today. The cost of forgetting is not bounded — the first release without
provenance sets the precedent that releases do not have provenance, and every subsequent one
inherits it.

## Framework position

`framework-registry.yaml` registers `slsa` with `mapping_deferred_to: REQ-0014`. That is
deliberate: SLSA governs the build pipeline that produces release artifacts, and mapping any
existing control to a SLSA level today would assert a build-integrity property of a build
that does not happen. When this requirement is implemented, the mapping is written and the
`mapping_deferred_to` is removed.

Related: NIST SSDF `PS.2.1` (verifying release integrity), `PS.3.1`/`PS.3.2` (archive
releases; collect and share provenance data), CIS v8.1 `16.4` (inventory of third-party
components) and `16.5` (up-to-date and trusted components), NIST CSF 2.0 `GV.SC`.
