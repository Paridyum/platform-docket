# RUN-0007 — Uploading the docket archive

ADR-0071 decides that the off-host store is Sync.com and holds only ciphertext. ADR-0072 decides
which node writes and what replicates. **This is the procedure**, and it exists because those two
decisions left the actual upload to a human reading a list.

## Do not copy files by hand

    docket store push ~/Sync/paridyum-docket

That is the whole operation. It copies `store/vault/` and nothing else, skips files already
current, and refuses in four situations before writing anything.

**The reason it is a command rather than a `cp` is that three of the four refusals are invisible
to a person doing it carefully.** A directory added to the store last month appears in no list; a
`keys/` uploaded once, months ago, is not visible in what you are uploading today; and a
half-backed-up register looks exactly like a complete one.

## What it refuses, and what each refusal is protecting

| Refusal | The accident |
| --- | --- |
| **Destination inside the store** | The store is the thing being uploaded. Also catches a *relative* path resolving back inside it — that one got past an earlier guard and wrote into the directory it was protecting. |
| **`keys/`, `index/` or `exports/` already at the destination** | The only check that looks at what is **already there**. A key uploaded once by hand cannot be destroyed afterwards, and destroying it is what erasure *is* (ADR-0069). |
| **An unclassified path in the store** | Nobody has ruled on whether it replicates. An upload that guesses is how something ends up published, or lost, by accident. |
| **A file that is not `.age`** | ADR-0071 §1: the extension is the contract. One plaintext file in a sensitive tree is personal data on a foreign consumer drive. Nothing is written when this fires — every file is checked before any file is copied. |
| **A register with no bundle behind it** | Run `docket vault backup` first, or the upload publishes a half archive and reports success. |

## The order, every time

```sh
docket check                       # the records are consistent
docket vault backup                # the register becomes ciphertext
docket store status                # exits non-zero if anything is at risk
docket store push ~/Sync/<folder>  # guarded copy
```

`store status` is the one worth putting in a shell prompt. It answers *what dies with this
machine*, which is a different question from *what could be uploaded*.

## "Uploaded" means written to a folder

`docket store push` fills the folder the vendor's client watches. **It does not reach Sync.com**,
and ADR-0071 is explicit that docket never will: there is no S3 endpoint and no API, only a
desktop agent replicating a directory.

So the last leg is the client's, and it is the leg that fails silently. Confirm it has finished
before treating anything as backed up.

**On this estate the client runs on the operator's Mac.** RUN-0005's Windows guest is for
RFC-0038's personal-drive migration and is not part of this procedure — the vendor ships a Mac
client, so docket's archive needs none of that machinery.

## What never goes, and why the list is short

`store/keys/` is the whole reason this runbook is careful. Everything else in the never-list is
recoverable or regenerable:

- `index/` — regenerated by `docket index`, and uploading it defeats ADR-0051's opaque folder
  naming by publishing a map from identifier to name. Note that ADR-0071 §4 warns file and folder
  *names* may not be encrypted by a zero-knowledge drive at all.
- `exports/` — regenerated by `docket team`; it is public data with a public home.
- `keys/` — **not recoverable and not regenerable.** A versioned store retains what you delete
  from it, so a key that reaches Sync can never be destroyed, and no erasure performed afterwards
  is real. This is not a caution; it is the mechanism failing silently.

## Before you trust any of it

**A backup that has never been restored is a belief, not a control** (ADR-0071 §3). The estate has
rehearsed the restore locally (`tests/node.rs`) and across a real machine boundary
(`rehearsal/rehearse.sh`, four containers, no shared filesystem). Neither touches Sync.com, because
no Linux client exists to touch it with.

**One manual rehearsal is still owed**, and DECISION-DEBT D-53 holds it: push a bundle, pull it
down on a machine that has never held the store, and restore from that copy. Until that has been
done once, what is proven is the cryptography rather than the transport.

## If the estate key is lost

Everything above is encrypted to it. Losing it loses the vault, the register bundle and any
escrow, regardless of how many copies of the ciphertext exist — RUN-0004's *"exactly one thing to
lose and exactly one thing to back up"*, working as intended.

**The one action worth taking today is confirming that key is retrievable from the password
manager on a machine that has never seen this laptop.** It is worth more than any additional copy
of the archive.
