# ADR-0018 — A deferred requirement is an artifact with a trigger, not a comment

## Status

**LOCKED** as of 2026-08-07. Cites ADR-0008; does **not** supersede it.

Held at `proposed` while the ADR-0008 question below was researched rather than argued.
The research settled it, and settled it against superseding:

**Requirements are a recognised artifact class, distinct from decisions.**
ISO/IEC/IEEE 29148 — the requirements-engineering standard — defines a well-formed
requirement as *necessary, implementation free, unambiguous, consistent, complete,
singular, feasible, traceable, verifiable, affordable and bounded*, and requires a
traceability matrix linking each requirement to its origin, design and tests. Three of
those characteristics are precisely what an ADR cannot carry:

- **implementation free** — a requirement states *what*; an ADR states *what was chosen*.
  REQ-0001 says runtime secrets live outside the repository; choosing Infisical would be
  an ADR.
- **singular** — one requirement, one statement. An ADR is one decision, with alternatives
  and costs.
- **traceable** — requires a stable addressable identifier, which is what a namespace is.

Established ADR practice draws the same line: an architectural decision *addresses a
functional or non-functional requirement that is architecturally significant*.
Requirements define what must be achieved; ADRs record how a choice addresses them.

And the failure mode is named explicitly in that practice: *"a common failure mode is
treating ADRs as the universal documentation format. ADRs capture decisions; runbooks
capture operations; design docs capture structure; READMEs capture how to use a thing."*

That is the resolution. ADR-0008 rejected `LAW-` because it **duplicated** existing types —
principles already in C-0001, enforceable rules already in C-0004. `REQ-` duplicates
nothing, and folding requirements into ADRs is the anti-pattern the field warns against.
The two artifacts are consistent, so this one cites ADR-0008 rather than superseding it.

**On locking rather than trialling further.** The original plan was to leave this
`proposed` for months and lock it with evidence. The same research reversed that: RFC and
ADR lifecycles differ deliberately — an RFC has a long feedback period with an explicit
deadline, an ADR is expected to move through discussion quickly and *"should not remain in
draft indefinitely"*. Twelve requirements already depend on this artifact, so the decision
was made in fact and only unrecorded in status, which is the state that guidance warns
against.

Sources: ISO/IEC/IEEE 29148:2018; adr.github.io; Microsoft Azure Well-Architected,
*Maintain an architecture decision record*.

## Context

Work that is understood but deliberately not done has nowhere to live in this repository.

The concrete case that forced it: Infisical is the right answer for runtime secret
management, and it is the right answer **later** — at the first service that needs a
database URL at runtime. Today there are no services, no deployments and no runtime
secrets, so adopting it now would be building infrastructure for a load that does not
exist. But the reasoning is non-obvious and hard-won: organisation-level GitHub Actions
secrets do not work for private repositories on the Free plan, so without something like
Infisical every repository needs its secrets set by hand, forever. That constraint will
be rediscovered painfully in six months if it is not written down.

There are four places it could go, and all four are wrong:

- **A `TODO` comment.** No author, no reason, no priority, no trigger. Six months on
  nobody trusts it. This is the failure mode the whole repository exists to prevent.
- **A GitHub Issue.** Issues are for scheduled work. An issue nobody will action for a
  year is either closed as stale or clutters the backlog permanently, and in both cases
  the reasoning is lost.
- **`DECISION-DEBT.md`.** Machine-generated by the `capture-open-loops` Stop hook
  (ADR-0011) and marked do-not-hand-edit. It records *open loops it detects*, not
  deliberate deferrals.
- **An RFC.** An RFC is a proposal for how to build something (ADR-0013 stage 2). A
  requirement is a statement of what the platform must eventually do, independent of
  solution. Conflating them is the specific confusion the industry guidance on
  requirements management warns against, and it would make `rfc.has_alternatives_section`
  nonsensical — a requirement has no alternatives, it has a problem.

### ADR-0008 already decided the principle

This is the part that matters most, and it cuts in favour of the pattern. ADR-0008's
central decision reads:

> A governance rule is adopted when it is enforceable now and governs something that
> exists now. **Everything else is recorded as deferred, with the trigger that would make
> it applicable**, rather than written as if already binding.

Deferral-with-a-trigger is therefore not a new idea being imported. It is already
Paridyum's decided position. What is missing is a *place to put one*.

Today ADR-0008's own deferrals live in a prose section headed
`### Deferred — governs what does not exist yet`. They cannot be enumerated, carry no
trigger metadata, have no review date, cannot be cross-referenced from code or from
another artifact, and nothing checks that a stated deferral has a trigger at all. The
principle is adopted; the mechanism is a paragraph.

### The ADR-0008 question

ADR-0008 rejected a second identifier scheme:

> `LAW-NNNN` was proposed as a second identifier scheme. Rejected: a second namespace
> alongside `C-`/`ADR-`/`STD-` fragments cross-referencing for no gain. The proposed laws
> are principles and already live in C-0001, or are enforceable rules and now live in
> C-0004.

`knowledge.no_duplicate_id_namespaces` enforces this at `error`, with the rationale *"A
second id scheme (LAW-, POLICY-) would fragment cross-referencing."*

Introducing `REQ-` has to answer that rejection rather than ignore it. The reading taken
here is that the rejection turns on **"for no gain"** and on the proposed laws **already
having homes** — principles to C-0001, enforceable rules to C-0004. Neither applies to a
deferred requirement: it has no existing home, and ADR-0008's own prose Deferred section
is the evidence. `LAW-` was rejected as a *duplicate*; `REQ-` fills a hole.

That was a reading rather than a certainty when this was drafted, and it is why the
artifact was held at `proposed` rather than locked on authoring. It was then checked
against the field rather than argued further, and the check supports it: requirements are
a distinct artifact class in ISO/IEC/IEEE 29148 and in ADR practice, and collapsing them
into decision records is a named anti-pattern. See *Status* for the evidence and sources.

Had the answer gone the other way, this ADR would have superseded ADR-0008 rather than
citing it. It cites.

### Why only one new type, and not the full model

The research this came from proposes seven stages — Observation, Idea, Requirement,
Proposal, Decision, Epic, Task — each with its own directory, and an eleven-state
requirement lifecycle. Most of that is rejected here, on ADR-0008's own precedent:

> A `.governance/` directory of nineteen policy files was proposed. Rejected as a
> duplicate… Most of those nineteen files would be empty for a year, and **empty
> scaffolding is worse than none because it advertises coverage that does not exist.**

`observations/`, `ideas/`, `epics/` and `issues/` would be exactly that. Paridyum is one
person, zero services and two repositories. A directory per maturity stage would be
mostly empty for a year and would advertise a process nobody is running. ADR-0013 makes
the same argument about requiring an RFC for every change: *"abandoned within a month, and
the abandonment discredits the process for the changes that needed it."*

## Decision

**Requirements are a first-class artifact type. Observations, ideas and scheduled work are
not.**

1. A new artifact type `requirement`, id prefix `REQ-`, in `requirements/`.
2. A new status `deferred`, valid **only** for `type: requirement`: the requirement is
   accepted as real but deliberately not scheduled.
3. A `deferred` requirement **must** carry a `trigger` — the condition that would make it
   current. An event, not a date. This is an `error`, because a deferred requirement
   without a trigger is precisely the `TODO` this ADR exists to replace.
4. An optional `review_date` reconsiders a deferral even if its trigger has not fired, so
   a badly-chosen trigger does not bury a requirement forever.
5. A requirement states **what**, never **how**. "The platform shall manage runtime
   secrets outside the repository" is a requirement; "use Infisical's Kubernetes operator"
   is a design and belongs in an RFC.
6. **Ideas and observations go in GitHub Issues** with a label. They are cheap, most die,
   and a file per idea is overhead that will be abandoned. **Scheduled work also goes in
   Issues** — ADR-0013 already defines the lifecycle from RFC through PRs, and duplicating
   it as `epics/` adds a second tracker to keep in sync.

### Lifecycle

`draft` → `proposed` → `accepted` (will be built) **or** `deferred` (real, not scheduled,
has a trigger). From `deferred`, either `accepted` when the trigger fires, or `deprecated`
if it stops being true. `superseded` when a later requirement replaces it.

Six states, all but one already in the schema. The eleven-state model in the source
research is right for an organisation with a requirements team and wrong for this one:
states nobody transitions between are ceremony, and ceremony is what gets abandoned.

### Traceability

`REQ-` closes the chain the repository could not previously express:

```
REQ-nnnn  what the platform must eventually do
   ↓
RFC-nnnn  how it might be done            (ADR-0013 stage 2)
   ↓
ADR-nnnn  what was decided                (ADR-0013 stage 3)
   ↓
Issue → PR → commit → release             (ADR-0013 stages 4–7)
```

`resolved_by` already exists for the RFC end of this. A requirement points forward the
same way.

## Consequences

**Accepted costs**

- **The backlog grows by one** — `knowledge.deferred_requirements_have_triggers`.
- **An eighth id prefix, and the prefix set is hardcoded in eight places.** Adding `REQ-`
  required coordinated edits to `knowledge.schema.json` (four patterns),
  `check-registry.schema.json`, `capture-open-loops.sh` and `check-knowledge.sh` (two
  patterns and the directory list). There is no single source of truth for the prefix set,
  so a ninth type will be equally error-prone and a missed site fails silently — an id
  that validates in one place and dangles in another. That is a real defect this ADR
  exposes and does not fix.
- **`requirements/` starts with one file.** One is not empty scaffolding, but it is close,
  and if it stays at one for a year then this ADR was wrong and should be superseded.
- **A requirement can become a place to put things instead of deciding them.** "Defer it"
  is an easier sentence than "we are not doing this." The `trigger` requirement is the
  guard: if you cannot name the condition, you are not deferring, you are avoiding.

**Gained**

- Deferred work has a home with an author, a reason, a trigger and a review date, and can
  be enumerated. ADR-0008's principle gets a mechanism.
- The Infisical reasoning — including that org-level GitHub secrets do not work for
  private repositories on Free — is captured at the moment it was understood rather than
  rediscovered.
- Requirements outlive the designs that satisfy them, which is the property that makes
  them worth separating from RFCs.

**Rejected alternatives**

- *The full seven-stage model with a directory per stage.* Rejected on ADR-0008's
  empty-scaffolding precedent and ADR-0013's process-abandonment argument. The stages are
  right as a maturity model; instantiating each as a directory is wrong at this size.
- *`OBS-` and `IDEA-` prefixes.* Rejected: observations are facts that rarely go stale and
  ideas mostly die, so both are better served by an issue tracker than by an artifact with
  frontmatter, a review, and an immutability rule.
- *Reuse `RFC-` with a `deferred` status.* Rejected: an RFC proposes a solution and is
  required to enumerate rejected alternatives. A requirement has neither, and overloading
  the type would make `rfc.has_alternatives_section` incoherent.
- *A single hand-maintained `REQUIREMENTS.md` ledger.* Rejected: no ids, so nothing can
  cross-reference an individual requirement, and no per-item status. It is the `TODO`
  problem at file scale.
- *Do nothing and put Infisical in a `TODO` comment.* Rejected, and it is worth stating
  explicitly because it is the default outcome. It is what this entire repository exists
  to prevent.
