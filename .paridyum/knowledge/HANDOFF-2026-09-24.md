## 1. ⛔ THE BUG — the inner tenancy boundary was missing, and 0014 restores it

**If you are touching `platform-tenancy/migrations/0012` or `0013`, or anything in tool-docket that
writes a person record, start here.**

### What was wrong

`0012_accounts_and_the_docket_instance_retrofit.sql` added `account_id uuid NOT NULL` to docket's
five person-bearing tables and **left the RLS policies at `tenant_id + has_operator_scope()`**,
describing `account_id` as a discriminator "the application layer filters on when serving one
instance".

No application layer filtered on it:

| Layer that could have held the inner boundary | Did it? |
| --- | --- |
| RLS policy on the five tables | no — the predicate was dropped |
| tool-docket application code | no — `account_id` is in **0** of its 74 Rust sources |
| lib-auth `assertAccount` (ADR-0038 D5 backstop) | no — returns early for operator sessions, by design |

A tenant running two dockets would have had one record set. GLO-0004 rates an account↔account
crossing *"catastrophic for that business, and it is their reputation, not ours."*

### How it happened — because this is the part worth not repeating

`HANDOFF-2026-09-21` §1 found two migrations both numbered `0011` and resolved the collision by
keeping the uncommitted `accounts` retrofit and deleting PR #9's
`0013_an_instance_is_an_account.sql`. **The deleted file carried the inner predicate and the five
`paridyum:rescope` directives. The surviving file carried neither.** The merge was correct about the
numbering — which is what everyone was looking at — and silently downgraded the security posture.

The header of the surviving file justified this by citing **ADR-0104 accepted cost 4**, which leaves
*per-instance operator grants* undecided. That is a different question. **Accepted cost 1** governs
and says the opposite: *"Every docket query and policy gains an inner predicate, permanently…
That is the price of the boundary being real rather than notional."*

### The gate caught it. Nobody ran the gate.

```

10 error(s), 3 warning(s)
$ check-migrations.sh --root <HEAD>               # same checks, committed state
Migration check passed (3 warning(s))
```

Green at `HEAD`, red in the tree, for four days. **Re-run the gate after resolving any migration
conflict** — a merge that picks one of two files is exactly the operation its checks exist for.

### What carries the fix: `0014_the_inner_boundary_the_retrofit_left_out.sql`

`0012` and `0013` are back to **exactly the bytes that were applied** — drift cleared, `migrate.py`
unblocked, REQ-0008 immutability intact. Everything the review found is in `0014`:

- five `paridyum:rescope … account` directives, and the inner predicate on all five docket policies;
- `release_events` gains `account_id NOT NULL` (+ FK, + index, + `rescope`) and its read policy
  becomes account-bounded — it was `scope tenant`, **passed the gate**, and leaked by join anyway:
  `release_id → releases.account_id` let any non-operator read every sibling instance's versions,
  failures and deploying subject;
- `releases_operator_write` drops the `account_id = current_account()` pin, which would have refused
  provisioning a tenant's *second* instance — the requirement ADR-0104 exists to serve;
- `accounts.id` gains `DEFAULT uuidv7()` (ADR-0078 D2/D3).

Its `down` restores the applied-0012/0013 state and **says in the file that doing so re-opens the
boundary**, because a reversal that quietly re-introduces a leak is the thing worth naming.

## 2. ⛔ docket's write path is broken NOW — this is the live problem

This was written as "do not apply yet". It was applied. The consequence is present tense:
**0012 added `account_id uuid NOT NULL` to docket's five tables and the adapter does not supply
it**, so every docket write fails. Reads are fine; pods are up. Applying `0014` will additionally
make those writes fail the RLS predicate — it does not make the situation worse in kind, and it
closes a real leak, so it should not wait on the adapter.

`tool-docket/src/adapters/pg.rs`:

- sets only `paridyum.tenant_id` and `paridyum.operator_scope` in `enter()`;
- inserts `(id, tenant_id, record)` / `(id, tenant_id, slug, record)`.

Every docket write fails the NOT NULL; every read and write additionally raises
`paridyum.account_id is not set`.

**This blocker predates the correction.** The NOT NULL column is in every draft of the retrofit,
including the deleted one. The retrofit was written without its only writer being updated — which is
why applying early broke docket rather than merely being premature.

**Recommended order from here:**

1. verify the two checksums in §1, then **`migrate.py apply`** to land `0014` — it closes the
   `release_events` leak and the missing predicate, and needs no application change to be correct;
2. **T-G.19** — the adapter learns an account, and seeds the `product='docket', slug='default'`
   row it will need (`accounts` is empty, so that row does not exist yet);
3. redeploy docket; writes return.

Full statement: `tool-docket/DECISION-DEBT.md` **D-70**.

## 3. Still undecided — do not answer this one in a migration

`releases_read` lets a non-operator tenant session read its own Release, because ADR-0100 D3 makes
`<host>/dashboard` a signed-in tenant surface. But `accounts` carries one policy, `accounts_operator`
(`FOR ALL`, requires operator scope) — and `product` lives **only** on `accounts`, deliberately,
because RFC-0015 forbids the second copy.

**So a dashboard session can read its Release and cannot name the product it is.** Either `accounts`
gains a SELECT policy for the owning account, or those sessions carry operator scope and ADR-0100 D3
means something narrower than it reads.

Left open on purpose: it is a decision about who may read what, and the artifact precedes the code.
Tracked as **T-G.20**. It blocks **T-G.9**.

## 4. If you are about to touch multitenancy, the three things worth knowing

1. **`tenants` has no RLS and that is correct** — `-- paridyum:scope platform`, no `tenant_id`
   column, so it never enters the checker's RLS loop. The row that *defines* a tenant cannot be
   tenant-scoped without a circularity (0001's own note).
2. **Every accessor RAISES rather than returning NULL** (ADR-0038), and **Postgres does not
   guarantee OR short-circuit inside an RLS predicate** — migration 0004 documents this and works
   around it with a throwaway uuid. A session that sets tenant and operator scope but not
   `paridyum.account_id` gets an error, not a wide read. That is the design; it reads as a puzzling
   failure at the first SELECT.
3. **Token verification already exists — do not write a second one.** `lib-auth`
   (`@paridyum/auth`) has `Verifier` (cached JWKS, issuer, expiry, and an explicit `aud` membership
   test written because jose's `audience` option is satisfied by *any* listed audience while Zitadel
   puts the client's own id in `aud`) and `withSessionContext` (`set_config` × 3, `SET LOCAL`,
   inside the transaction, all UUID-validated).
